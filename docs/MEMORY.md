# Bilusic 项目长期记忆（精简版）

## 架构约定
- Bilibili 仅做音频引擎；元数据来自音乐服务插件（QQ 音乐/网易云等内置）。双 trait：`MetadataSource`(search/get_track/get_lyrics/home) + `AudioEngine`(find_stream_by_id/query)，由 `Coordinator` 编排。`PluginCapabilities` 位标志。跨源：元数据 `engine_hint="bilibili"` → 走 B 站引擎。本地流代理 `:9527`（axum），前端 `proxyStreamUrl()` 包裹直链。

## 插件系统技术选型
- **不引入 deno_core/V8、不动态加载 Rust dylib**。原生音源 = 编译期 Rust trait（`impl MetadataSource/AudioEngine/Lyrics`）。
- **第三方三线**：① `declarative`（零代码，默认，宿主 reqwest+JSONPath）；② `wasm`（wasmtime，feature=`wasm` 门控，host functions `bilusic.host_http_get` async / `host_log`）；③ `js`（rquickjs，**默认开启** feature=`js`）。`load_runtime_plugin(manifest)` 为统一接缝，按 `runtime` 分发。
- **JS HTTP host 用「Tauri 全局兜底 handle」拿 tokio runtime（不要用 `Handle::current/try_current`）**：`HttpHost::with_default_client()` 内部 `tauri::async_runtime::handle().inner().clone()`——后者源码（Tauri 2.11.5 `async_runtime.rs:265`）是 `RUNTIME.get_or_init(default_runtime)`，thread-agnostic 的 lazy-init 全局入口；**任何线程**调都成功（tao 主线程、tokio worker、spawn_blocking、测试线程统一适用）。`RuntimeHandle::inner()` 返回 `&TokioHandle`，而 `TokioHandle = tokio::runtime::Handle` 的 re-export（`async_runtime.rs:14`），类型完全一致可直接存 `HttpHost.handle: tokio::runtime::Handle`。**绝不要**用 `tokio::runtime::Handle::current()/try_current()` 拿 handle——前者 panic（"there is no reactor running"），后者返 Err；两者都是 thread-local，仅在 runtime worker 上有值。Tauri 2 的 sync `.setup` 闭包在 tao 主线程跑（**不在** tokio runtime 内，与 tokio worker 平行），所以 setup 内部即使是 init 也拿不到 `Handle::current`。**两次踩坑（N11a panic + N11b fallback）后才能确定**唯一稳定路径。

- **JS 插件作者语法红线（QuickJS 0.12 / Bellard quickjs 只到 ES2017~ES2018）**：禁用 `??`(nullish coalescing)/`?.`(optional chaining)/numeric separator(`1_000`)/`#` 私有字段/顶层 await/可选 `catch` 绑定。整文件含任一不支持语法 → `rquickjs` 加载即 SyntaxError → `main` 未定义 → 所有 op 集体报「Exception generated by QuickJS」。N11e 踩坑：酷我 `index.js` 用了 `30_000`(`line 30`) 与 `item.time ?? item.t ?? ...`(`line 311`) 两处，导致首页空白+搜索报错。宿主契约文档（`js_runtime.rs` 模块注释 + `plugins-examples/js/README.md`）应**显式列出**这些禁用项。**校验手段**：`/tmp/kuwo-quickjs-smoketest.cjs` 用 `quickjs-emscripten` 真实引擎、每 op 独立 fresh context 冒烟 5 op（search/home/get_track/toplist/get_lyrics）；PRELUDE 的 `log` 桩**不能**用 `console`（sandbox 无 `console`），用 no-op 或累积数组，否则会假阳性 FAIL。

- **JS 插件 `main()` 必须「任何 throw 都不能逃出 main 边界」**——这是硬契约。rquickjs 0.12 把任何未捕获的 JS 异常都报为「Exception generated by QuickJS」、宿主以 `JS 插件 main() 抛错：{e}` 上抛，行为对用户等同 fail-stop。**每个 op 调用必须用 try/catch 包**（legacy dispatch 路径同样——`op:null` / `op:''` 时也会进 legacy），`out()` 自身 try/catch（防 JSON.stringify 在循环引用下炸），catch handler 不依赖 `bilusic.log` 会成功（logger 也坏掉时不能让它放大异常——双重 try/catch）。N11g 防御性重写：kuwo `index.js::main()` 顶层 try/catch 包整个函数体 + `safe(opName, fallback, fn)` 工具包每个 op + `out()` 自带 try/catch；mock 验证 `httpGet throws` / `httpGet 返回非 JSON 字符串` / `bilusic.log throws` 三种异常路径均不让异常逃出。**协同契约**：JS 插件可以抛异常，宿主不能把异常「如实」上抛——任何 escape 都直接断该端点的搜索/详情。所以 host 的 host_http_* 错误返回也得是 `{ok:false,error}` 而非 throw。

- **JS 插件 `home()` 契约是嵌套 `{"home":{playlists,new_songs,new_albums,artists}}`**（不是扁平 feed）。宿主 `js_runtime.rs::home()` 必须先 `map.remove("home")` 解包内层再取各 feed 字段，否则 `HomeFeed` 恒空、首页空白。N11e 修复前只认扁平形状 → 所有返回嵌套 `home` 的 JS 插件首页都空。契约见模块文档 `js_runtime.rs:62` + 示例 `plugins-examples/js/plugin.js:107`。

- **切换元数据源必须清首页/榜单缓存（N11f）**：前后端首页/榜单缓存都按 source 分桶（前端 `bilusic.cache.home_feed.${source}`，后端 `home:<id>`/`toplist:<id>`），正常不串源；但后端 `set_active_metadata` 在源切换瞬间若读到旧 active id 可能把旧源 feed 写进新源 key（竞态），且前端 localStorage 跨重启持久化会保留「污染」缓存 → 首页内容跟不上源切换。**修复**：`set_active_metadata` 调 `home_cache.clear()`+`toplist_cache.clear()`（`cache.rs` 新增 `clear()`）；前端 `setMetadataSource` 调 `invalidateHomeCache(id)` 清 incoming source 的 localStorage 首页+榜单缓存（不动其它源）。

- **酷我首页 artists「运行时优先 + baked 兜底」(N11i-5)**：N11i-4 是纯 baked；N11i-5 用户改主意——希望首页先用 Secret+Cookie+Chrome 151 UA 三件套调 `/api/www/artist/artistInfo`，**任何错**（HTTP throw / `!resp.ok` / 空 body / JSON parse fail / `success:false` / `code!=200/0` / 空 list / list 行缺 `{id,name}`）都 fallback 到 `BAKED_ARTISTS`。**实现**：`index.js` 顶部新增 5 个 const（`ARTIST_UA` Chrome 151 / `ARTIST_SECRET: '4812c9ca5a12265...3dce83'` / `ARTIST_COOKIE: 'Hm_Iuvt_...=kBBhK5Nz...'` / `ARTIST_REFERER: 'http://www.kuwo.cn/rankList'` / `ARTIST_INFO_URL` 含那 9 个 qs 参数 + `reqId=` 占位）+ 3 helper（`pickArtistList` 兼容 `data.artistList`/`artistList`/顶层数组 / `artistReqId` v4 UUID-ish / `artistInfoHeaders` 拼那 10 个 header）+ `artistInfoOp()` 函数（**任意**失败路径打 warn + `return null`，**绝不抛到 main 外**）；`homeOp` artists 部分改成 `live || baked` + try/catch 外层兜底（future refactor 也安全）；`BAKED_ARTISTS`/`BAKED_ARTISTS_RAW` 保留作 fallback 源。**双重日志**：(1) `enter get <完整 URL>`；(2) 6 种失败路径各打一句带原因的 warn；(3) `home[done] artists source=live|baked len=N` 一目了然 source。**校验**：`/tmp/kuwo-artist-smoketest.cjs` 4 mock（全 4/4 PASS：A 真实 2 行 / B illegal / C code=400 / D TCP 超时）；`/tmp/kuwo-newep-smoketest.cjs` 9/9 PASS（不破回归）；`cargo test --features js --lib` 20 passed。**Secret+Cookie 直编码进插件**——N11i-4 担心轮转，但实际**只要旋转就自行失效**会触发 baked fallback，不让首页空白，等用户察觉更新插件即可（成本低于 runtime 拒全部 artists 永远 fallback）。**通用 lesson**：① 任何 web API「**运行时优先 + 快照兜底**」是商业接口的稳健模式——比纯 baked 更接近用户期待的数据实时性，比纯 runtime 更强韧；② fallback 触发条件要**显式列尽**（函数注释写清 6+ 种），下个维护者不用猜「为啥 fallback 了」；③ 「**任意 throw 不外逸 main**」是 JS 插件硬契约——artistInfoOp + homeOp 两层 try/catch 是 N11g 防御性 main 模板的纵深；④ 失败路径要**留下带具体原因的 warn 日志**——「why we fell back」日志比「fell back」一行更有价值；⑤ 内联 Secret/Cookie 到插件源是 trade-off（用户改起来麻烦 vs 启动即可用）——长期应配置化（manifest 字段 / 配置中心），但 MVP 阶段 inline + 重发插件版本即可。
  - **酷我首页 artists baked data 源（N11i-4 临时方案）**：`/api/www/artist/artistInfo` 端点对带 `Secret` 官方签名 + 真实 Baidu-Tongji cookie + Chrome 151 UA 的请求放行（沙箱 curl 一次拿到 60 个 artists），但**桌面客户端不该造这三件**——Secret 轮转、cookie 是 site-scoped。所以这个端点当**build-time snapshot 源**：`apps/desktop/plugins/kuwo/data/artists-raw.json`（25KB 完整 upstream 响应）+ `data/artists-baked.json`（17.6KB 标准化提取）+ `index.js` 顶部 inline 14KB compact `BAKED_ARTISTS_RAW` 字符串字面量 + `BAKED_ARTISTS` IIFE 规范化 60 条。`homeOp` 直接读 `BAKED_ARTISTS`，**不发任何 artist HTTP 请求**。`scripts/regenerate-artists.sh` 提供季度 re-bake 工具（`KUWO_SECRET` / `KUWO_COOKIE` 环境变量覆盖默认值，自动 `uuidgen` reqId，三档 exit 区分 curl/JSON/shape 错误）。**之前 9 个手挑的 `POPULAR_ARTISTS` 数组已删**——占位 cover URL 误导，baked 真数据更稳。**关键观察**：同一 `/api/www/...` 路径段下，**带 Secret 就能过、不带就 illegal**——Secret 才是真正的"门禁钥匙"，N11h 一直 illegal（无 Secret）+ N11i-4 一发就过（带 Secret）。N11i-5 已把这个 baked 退化成 fallback。
- **「运行时优先 + baked 兜底」日志规约（一次错源日志 / 禁止二次放大）**：(1) **真实错误处**（如 `bangMusicListOp` 内 `code != 200` / `success:false` / 空 list / HTTP throw）在能附原因的最近一层打 warn——保留诊断信号（Secret 旋转/IP 风控最直接的可观察线索，丢失后无法察觉 baked 触发原因）。(2) **fallback 切换点**（`homeOp` 内 `live || baked`）**禁止**再打 "using baked fallback" 之类二次放大日志——运行时错误已经在源日志输出，每榜重复一遍就是噪音 ×6（一次首页加载就刷屏）。改用**单行注释解释「why we fell back quietly」**即可。N11t：用户截 17 条重复 warn 反馈后删 homeOp newSongs + bang 循环两处二次放大，保留 bang 真实错误源——首页信号从 17 条降到 6 条（仅 bang 接口真实失败）。**通用 lesson**：任何带 fallback 的 op 链路都应遵循 "fail 源 + fallback 切换" 双段日志规约——前者记一次 why，后者沉默。
- **「清除本地缓存」按钮 UX：reload 前必须 ≥800ms 延迟**：N11p 加 `handleClearLocalCache()` 时 toast 后**立即** `window.location.reload()`，toast 根本没有机会渲染就被刷页——用户看到"已经点了怎么没反应"。**修复**：`window.setTimeout(() => window.location.reload(), 900)` 让 toast 进入 React commit 阶段并 paint，再 reload。TOAST_TTL_MS=4500ms（4.5s 自动消失），900ms 远小于 TTL，给用户 **~3.6s** 看清「已清除本地缓存，正在重新加载…」。**适用任何 "toast → reload/navigate" 路径**——任何销毁当前 view 的反馈都要先等 paint，别让 toast 沦为"理论成功"。
- **「搜索页热门推荐」= kuwo `toplistOp(topid)` 的前端入口（N11u）**：kuwo plugin 早就实现 `toplistOp(topid)` 走 `searchOp(榜单名, 1)` 拉 top songs（topid 1-9 → 热歌榜/新歌榜/飙升榜/电音榜/ACG榜/粤语榜/欧美榜/韩语榜/日语榜），host 命令 `metadata_toplist` + 前端 `metadataToplist(topid)` 早就注册导出，但**前端零 usage**——只是一个未接的"扳机没扣"。`Search.tsx` 加 `KUWO_CHARTS` 常量与 chip UI + chart view state（`{topid, title, items}`）作为 kuwo-only 入口，仅 `metadataSource === 'kuwo'` 显示。**关键约束**：(1) chart view 与 keyword search **互斥**——`submit()` 先 `setChartView(null)`；(2) chart 模式下 `sorted` 不参与（toplist 已按 rank 排好），禁用 infinite scroll + 排序按钮；(3) chart 模式独立 loading/error/empty state。**冗余风险**：`KUWO_CHARTS`（前端）与 `kuwo/index.js::toplistOp.queries`（插件）是 redundant——理想提到 plugin manifest（`plugin.json`）让前端读，省人工同步。**跨源限制**：`metadataToplist` 现在是 kuwo-specific 合约（topid 1-9 是 kuwo 内部约定）；其它元数据源要加 chip 需先建模**统一 topid 合约**（不然同一 int 在不同源语义完全不同）。
- **酷我 JS 插件搜索端点 N11i-3 切 `/search/searchMusicBykeyWord`（N11h 选错的真根因）**：原 `search.kuwo.cn/KuwoMobileApi/searchMusicByKeyWord` mobile 老接口已死。**N11h 选的 `www.kuwo.cn/api/www/search/searchMusicBykeyWord` 是站点后台内部 API**——CSRF + 浏览器指纹双层反爬，再完美 anonymous + 完整浏览器 header 也一律 `success:false, message:"The request is illegal!"`。**真正能用的是 `www.kuwo.cn/search/searchMusicBykeyWord`**——Kuwo 前端搜索页面默认调用的宽容接口，Postman 默认 header 直接拿到结果。**必备 query 参数**（Postman 截到的固定 9 个）：`vipver=1&client=kt&ft=music&cluster=0&strategy=2012&encoding=utf8&rformat=json&mobi=1&issubtitle=1&show_copyright_off=1`；再拼 `&pn=1&rn=20&all=<urlencoded_query>`（**用 `all=` 不用 `key=`**——这一端点特有字段名，掉进 `key=` 就会拿不到 `data`）。`Referer: https://www.kuwo.cn/search/list?key=...`；scheme 优先 https（自动 redirect）。**匿名 + 完整 Chrome 浏览器 header 集沿用 N11i-2**不变（Host 由 reqwest 自动填）。**响应形状**主流是 `data.abslist`（已在 N11h songlistToTracks 兼容 rid/name/artist/album/albumpic/duration mm:ss）；变体还有 `data.songs` / `data.list` / 顶层数组。**`pickSongList(data)` ladder 按"端点演化时间倒序"**列 8 种路径（`data.abslist` 优先 → `data.songs` → `data.list` → `data.musicList` 等 + 顶层变体 + 顶层数组兜底）；后续 Kuwo 再换字段，加一行 ladder 即可。**新增 `status:0` 拒绝识别**（`/search/` 端点不用 success:false 而用 `status:0`+`msg`）。**`get_track`/`get_lyrics`/`home`/`toplist` 暂不切端点**——它们仍走 N11h `/api/www/...`（虽然严格，但用户测试没报 illegal，可能这些端点反爬较弱或者顺序未触发——之后再单独决策）。**沙箱 IP 永远被风控，所有 KUWO `*` URL 的 e2e 都必须在用户国内机器**；本地只验解析层：smoke test 模板 `/tmp/kuwo-newep-smoketest.cjs`（9 mock：A `data.abslist` 2首 / B `data.songs` 1首 / C `data.list` 1首 / D 顶层数组 3首 / E illegal / F status=0 / G 空 abslist / H JSON parse fail / I HTTP fail = **9/9 PASS**）。**通用 lesson**：(1) 任何 web API 接入第一步应是**真实浏览器交互 + Postman 抓包看实际请求**——不要从文档/相似路径推测（我们猜了 4 个节点才纠对端点）。(2) 同一站点多个端点反爬严格度可能差很大，**从最宽容的入口端点入手**，进不去再逐级深入。

- **JS 插件诊断日志"双路输出"（N11i）——所有 JS 插件 host binding 的设计模板**：宿主 `bilusic.log` 之前只走 rquickjs 内置 `console.*`（**只输出到后端 stderr**，前端 DevTools Console 不可见）——这是用户报"不知道为啥没结果"的最大盲区。**修复**：宿主新增 `__host_log` host binding（`make_log_fn`），始终 `eprintln!` 兜底 + 若 `HttpHost.app_handle: Option<tauri::AppHandle>` 存在则 `WebviewWindow::eval("console.{error|warn|log}(...)")` 镜像到 webview DevTools。`HttpHost` 多 `with_default_client_and_app(app)` 工厂；`PluginHost::init` 多收 `&AppHandle` 参数（`lib.rs::setup` 透传 `app.handle()`）。`level` **必须白名单**（error/warn/log），因为会拼成 JS 函数名——任何用户控制的字符串都是注入面；`msg` 必须 `serde_json::to_string` JSON-编码防双引号逃逸。**JS 插件作者最佳实践**：每个 op 入口打 `bilusic.log('info', '[plugin][op] enter ...')`，关键决策点（HTTP 状态 / 解析成功失败 / 空 list / illegal message / tracks 数 + 首项样例）打 `info`/`warn`，所有 log 加 `[<plugin>][<op>]` 前缀便于 Console filter 一键过滤。**测试**：`Scope.withScope` + `quickjs-emscripten` 真实引擎跑 mock 场景（CSRF illegal / 空 list / 真实一首 / HTTP 失败 / 空 body / JSON 解析失败），断言预期 substring 命中 + tracks 数。**绝不再写"只走 rquickjs console.*" 的宿主 binding**——那是用户看不见的 log。**适用任何新增 host binding（除 http 之外，将来插件上报 metric、play_state 等）都应照此模板双路**。

## 播放队列与歌词（player store 契约）
- **队列导航 vs 单首播放语义不可混用（N11v 根因）**：`stores/player.ts` 里 **`playAt(i)`** = 队列内原位解析+播放，**绝不替换队列**（只更新 `queue[i].resolved`）；`jumpTo` / `next` / `prev` / `removeAt`(wasCurrent 自动续播) 全部必须走 `playAt`。**`resolveAndPlay(track)`** = `set({ queue: [track], index: 0 })`，**清空队列替换为单首**——只给外部「点一首歌就播」入口用（Search / Home / Playlist / PlaylistDetail）。历史坑：在队列导航里误调 `resolveAndPlay`（当目标项 `resolved:null` 时）会把整个队列清空成单首。**`playAt` 带 `get().index === i` 守卫**，防止异步解析期间用户又跳走造成竞态。队列仅在「删除/清空」（`removeAt` / `clearQueue`）时移出项，播放/跳转不改变队列构成。
- **队列 UI 交互（N11s）**：`QueueDrawer.tsx` 行 **无 onClick**（点击行不切歌，避免浏览误触）；hover 显示一个**显式「播放这首」按钮**（`PlayIcon`）触发 `jumpTo(i)`。保留拖拽手柄重排、删除按钮、当前项高亮（accent-500 环 + 文字加粗变色）。i18n `player.jumpTo`。
- **NowPlaying 歌词 = 纯文本、零高亮（N11r 强约束）**：用户明确「不要加粗/变亮/active 行在动」。歌词区所有行统一 `text-sm text-fg/70`，**无加粗、无变亮、无 active 视觉差**；无 `scrollIntoView`、无偏移微调、无自动滚动。这是纯浏览模式——B 站音源时长与歌词 LRC 时间戳恒定时移，无法精确同步，故放弃同步只展示文本。任何「当前行高亮/字号变化」相关效果都不要加。**关键 lesson**：「自动滚动」错觉常来自 active 行字号变化（text-sm↔text-xl）或顶部 padding，纯浏览必须用同字号 + 仅颜色区分，且结局是用户连颜色区分都不要。
- **弹层/Popover 通用规则（N11x 强烈推荐 Portal）**：弹层**默认就该走 `createPortal(node, document.body) + position: fixed` + `getBoundingClientRect()` 手算位置**，别再用父级 `absolute` 定位。**任何父级 `overflow / overflow-x:auto / [contain:paint] / transform / filter / opacity<1` 都会切断或锁住 child 的 fixed containing block / 越界 paint**——Home 横向滚动行的 `overflow-x-auto` 就直接裁了 AddToPlaylistMenu popover 左半边（"Add to queue" → "d to queue"）。手算位置时：① `popPos` 初始 `null`（测量前不在 (0,0) 闪烁）；② `scroll` 监听必须 `capture: true` 才能接住非窗口祖先滚动；③ outside-click 监听需同时含 `wrapper ref` + `popoverRef`，否则点 popover 内部会被立刻关掉；④ 视口边界反转（右边超出 → 改 `left = r.left`，底边超出 → 弹到按钮上方）。**别依赖父级 absolute，再花式边界都不如 Portal 一劳永逸。** 想再省事用 `@floating-ui/react-dom` / Radix Popper，已处理 boundary/flip/offset/shift 一整套。

## all_plugins 三段式（builtin source-of-truth = builtin_ids）
- `builtin_ids`：`init()` 末尾遍历 `metadata.list_all()+engines.list()` 填入的 Rust 编译期 id 集合，**正向**判定 `builtin`（不用 manifest_ids 反向，否则同 id bundled stub 会把内置翻成第三方）。
- pass1 注册 adapters；pass2 枚举 Registry（`builtin=builtin_ids.contains`、`removable=!builtin && !BUNDLED_NON_REMOVABLE_IDS`）；pass3 emit stub 行——**包含同 id bundled 清单**（其 `builtin=false` → 第三方徽章；**所有 stub `removable=true`（含 bundled，全部显示卸载按钮）**）。`uninstall()`：user_dir 下 stub 真删；bundled/dev stub 改写入 `hidden` 会话隐藏集合（不再报错，下次启动复现）。`all_plugins()` pass3 跳过 `hidden` 中的 stub。`PluginHost.hidden: RwLock<HashSet>`。
- **同 id 双行**：Rust 内置 + 同 id bundled stub **都显示**（内置行 Built-in 徽章；bundled stub 行 第三方+Stub 徽章）。lrclib 两侧都是 stub（现多一行第三方 stub）；**kuwo 已退役内置骨架、改为 JS 插件**（真实可用，`apps/desktop/plugins/kuwo/`）。**kugou / spotify / ytmusic 三个内置骨架已于 N14 彻底删除**（永远 NOT_IMPL、纯死代码），不再走 built-in + stub 双行模型。
- **同 id 双行的身份 = `kind:id:stub`**：卸载/乐观更新/主动源回退触发都必须用三元组匹配，**不能**只比 `kind+id`，否则一次操作会误删双行；metadata/engine 主动源回退需额外 `!item.stub` 门控（隐藏 stub 不应切走由内置 adapter 支撑的 active 源）。后端契约：`uninstall` 只动 stub（写 `hidden` 或删 user_dir 子目录），永不动内置 registry。回归测试 `uninstalling_same_id_bundled_stub_leaves_builtin_intact`。
- **导入判重 = `target.join("plugin.json").exists()`**（不是 `target.exists()`）：空/残留目录（无 manifest）必须可被新导入覆盖——否则用户对「同内置 id 的第三方插件」的导入会被一个无 UI 入口的死文件夹永久卡住。真·已注册插件（有 plugin.json）仍拦，提示「请先卸载」。
- **命名空间隔离（A 方案，用户拍板）**：import 拒绝同内置 id 的第三方插件。内置 adapter 在 `lib.rs:70-79` 优先 register，pass1 看到同 id 就 `continue`，所以用户导入的同 id 插件永远只是 stub 展示行、运行时不被调用。固定契约：用户想用自己的版本 = 把 `plugin.json` 的 id 改成唯一的（`kuwo_custom` 等）。`import()` 在 runtime 校验通过后、target 判重前增加 `if builtin_ids.contains(&id)` 短路。错误消息包含具体 id + 改名方向。回归测试 `import_rejects_id_that_collides_with_builtin`。**潜在 B 方案**（init 顺序对调，用户先注册 / 内置仅占空 id）与 **C 方案**（per-built-in disable toggle）均未实现，留作未来选项。
- `BUNDLED_NON_REMOVABLE_IDS=["itunes-declarative"]`（真 release，不可卸）。
- 徽章三色：`builtin`(accent 紫) / 第三方(sky 蓝) / `stub`(amber 琥珀，可与第三方共存)。

## 网易云 / weapi 反爬 API 契约（N11z 起改用 ncm-api-rs SDK）

- **eapi vs weapi 通道陷阱（已踩坑）**：`ncm-api-rs` 便捷方法（`.cloudsearch()`/`.lyric()` 等）默认走 **eapi**（`interface.music.163.com/eapi/...`），对**未登录**连接 TCP 层静默 RST，reqwest 报 `error sending request`（无 HTTP 响应）。`song_detail`/`lyric`/`playlist_detail` 内部已是 weapi 不受影响。**凡需匿名搜索/首页，必须走 `client.request(uri, data, RequestOption{crypto:CryptoType::Weapi,..})` 到 `music.163.com/weapi/...`**——见 `netease_metadata.rs::weapi_request` helper。
- （历史）手写 weapi 死因 = crypto 常量错（modulus 尾 `…c7e0c7e0c7e0c7e0c7` 占位串）。该手写方案已被 N11z 推翻，仅作"为何用 SDK"的教训保留。算法原为 `params = base64(AES_CBC(base64(AES_CBC(json, PRESET_KEY)), secKey))`，`encSecKey = rsa(secKey_reversed, EXP, MODULUS)`，POST 带 `Referer=https://music.163.com` + Chrome UA。
